# Screen understanding — 1.5.11

Floating mode previously reset app guidance to off whenever summoned and required a manually selected app. Most screen questions consequently reached the provider without an image. Guidance prompts also emphasized OCR/control IDs rather than diagram interpretation.

Screen and diagram questions now attach a fresh JPEG of the front visible app window. ScreenGuidance tracks the last foreground external app across Iris composer/desktop focus. Floating guidance defaults to automatic current-app selection; its eye settings can disable sharing or pin a chosen app. Normal desktop/notch visual requests use the same capture path. Ordinary questions do not capture. Floating follow-ups with a visible-reference word refresh the snapshot; explicit no-capture language is honored. No background polling or screenshot history is added.

Only one window is captured, on the display with the largest intersection. Other apps and Iris overlays are excluded. OCR failure no longer discards an otherwise valid image. The image is passed through existing OpenAI Responses, Gemini inlineData, and local multimodal formats. Local models must support vision. Iris.md and per-image instructions explain visual diagram labeling with real image coordinates; desktop-only requests answer in chat, floating requests can draw labels/arrows. Stale screen-bound annotations are rejected after clicks, navigation, app changes, display changes, window movement or timeout.

Validation: Debug and Release builds succeed. 23 focused offline tests pass, including request detection, explicit no-capture language, image payloads for all three providers, annotation bounds, multi-monitor mapping and stale-window rejection. After refreshing Screen Recording through System Settings with the owner’s Touch ID approval, a floating-mode synthetic-diagram request completed through Gemini and the drawOnScreen execution reported success. Exact label placement was not visually verified after subsequent scrolling invalidated the snapshot; builds are ad hoc signed, not Apple-notarized. Updating an ad hoc build changes its code hash, so macOS may require Screen Recording and Keychain approval again. Existing TCC records and user data are not reset.
